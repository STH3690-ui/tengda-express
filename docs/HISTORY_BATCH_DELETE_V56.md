# V55 删除历史修复（V56 增量）

## 问题与行为

V55 的预览 RPC 对每个根业务执行存在性检查，旧订单已物理缺失时直接报错；页面没有独立的历史隐藏状态，因此不能清理该类日志，关联产生的新 V54 标记也会再次出现在历史列表。

本次页面仅保留全选复选框、单条复选框和“删除已选”按钮。点击后只打开一个确认对话框，填写一个统一原因，按一次“确认删除”提交整个选择；无关联预览请求、无逐条确认、无额外输入确认文字。手机端保留清晰的大按钮和简洁卡片。

`td_delete_history_batch_v56` 在数据库验证激活管理员、原因至少3字和确认标志；规范化业务 UUID 列表，验证所选对象确实存在于删除历史/业务标记/既有历史隐藏中。一次最多50000条，整个批次共用原因和请求 UUID。

## 关联与财务保护

- 原业务存在：复用 V55 的专属关联计划和 V54 标记写入，保护共享包裹、客户、正常订单、共享结算及独立收款。
- 原业务不存在：不会从日志快照中的客户、商品、金额、电话或其他字段推断关联。仅从所选真实 UUID 出发，匹配仍存在的 `order_id`、结构化 `TD_ORDER_IDS`、`parcel_id` 等准确关系；没有准确关系时只隐藏该条历史。
- 缺失订单可清理仍以该 UUID 为外键的包裹/流水；缺失包裹可清理仍以其 UUID 为外键的取件。不会反向清理正常订单，不会按同客户扫描清空业务。
- 最小历史隐藏表 `td_history_hidden_v56` 记录业务表、UUID、操作者、原因、时间和请求编号。所选历史和本次新增关联标记均隐藏，避免清理后产生替代历史卡片。底层原日志、原业务快照和财务凭证保持不变。
- 私有请求审计仅保存规范化选择、操作者、统一原因和结果，用于网络重试幂等。新请求重复清理同一记录也不重复改库存、金额或添加业务标记。
- 相关业务表在同一事务内锁定，防止计划计算期间插入新关联；任意业务标记、历史标记或请求审计失败，整批回滚。
- V54 普通列表、日/周/月/年及员工统计过滤继续生效；V55 结算与收款凭证业务过滤继续复用。

## 文件与权限

完整增量 SQL：[`sql/history-batch-delete-v56.sql`](../sql/history-batch-delete-v56.sql)，前置为 V54 + V55；不重复安装旧版本。

修改 `index.html` 及镜像、Netlify 表/RPC 允许列表，更新 Node 和手机浏览器回归，新增真实数据库回归 `tests/history-batch-delete-v56.sql`。

公开 RPC 为 SECURITY INVOKER，受控实现放在 `td_private`，固定空 search_path；anon 不可执行。历史表启用 RLS，只有管理员可读取，客户端无写入/删除权限；私有请求表不开放客户端访问。

V55 旧预览/确认 RPC 保留以兼容旧客户端；新页面不再调用它们。内部关联计划仅扩展缺失根 UUID 的准确关系处理；旧正常根业务行为不变。
