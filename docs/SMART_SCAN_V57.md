# V3.2 智能扫码 POS / V57

## 交付和启用边界

新增智能扫码入口，保留现有15个主页入口（原14个加扫码），四个子功能：入库、查询、取件和记录。只向具有现有 `parcel_create` / `pickup_create` 的员工显示相应入口；收款还需 `finance_create`。无新账号授权类型，不修改原权限和账务规则。

**代码部署不等于数据库启用。** V57 迁移需要管理员审查批准；本次不执行正式数据库迁移。未安装时，页面明确提示“需要安装经审批的 V57 SQL”，服务检查失败后不会发起任何扫码业务写入，原入库/取件/财务页面继续工作。

完整、一次性增量 SQL：[20261113131906_smart_scan_pos_v57.sql](../supabase/migrations/20261113131906_smart_scan_pos_v57.sql)。前置条件：V32、V50 权限、旧版删除标记、V54/V55/V56。不重复执行旧迁移，不删除或修正历史数据。正式库只读查询确认了原 V32 RPC 和旧版标记字段。

## 业务行为

- 点击开启后才请求后置摄像头；ZXing 0.21.3 本地资源连续解码 Code128、Code39、EAN13、EAN8、QR，另开放 ITF、Codabar、UPC、DataMatrix、PDF417。后五类需真实快递单补测。
- 支持摄像头选择、设备支持时手电筒、停止、提示音/震动、USB/蓝牙 HID 的 Enter 后缀及手动输入。聚焦业务输入框时不会被全局扫码枪监听劫持。
- 页面隐藏、退出或路由切换释放摄像头。后台恢复需员工再次点击开启，不暗中重新授权。
- 运单 NFKC、去首尾空白、转大写，限制4–64位英文字母、数字、短横线。拒绝网址、脚本和其他指令，不解析URL、客户姓名或电话。
- 所有查询按规范化运单从数据库精确匹配；不受现有页面分页/加载上限影响。不推断客户。多个同运单历史记录只展示候选，禁止自动入库/取件，需在原业务中人工核对。
- 入库待办可编辑类别、件数、重量、备注、图片，人工搜索并明确选客户；可展开原有客户保存表单新建后再搜索。最多100条，一次确认；每条返回成功/失败。成功项移除，失败项保留。
- 图片复用原 Storage 上传，仅在包裹已提交后上传，图片失败不误报包裹失败、不重新插入包裹；结果显示上传状态，并可打开原包裹照片页面补传。网络响应丢失后的图片需人工核对补传。
- 查询展示状态、客户、件数、重量、类别、到站时间和真实 FK 对应的旧取件记录/批次明细，不改变库存或财务。唯一写入是必要扫码审计。
- 取件连续加入同一客户清单，可移除、统一重新称重、修改单价和实收。默认7000 MMK/kg，实收默认0（必须明确填写）。按十进制整数精度计算预览，避免浮点差一分钱；最终数据库 V32 计算权威。
- 取件确认弹窗明确列出件数、重量、应收、实收、欠款；扫描不会收款。V57 锁定并验证剩余件数、客户、所有旧/新删除标记后调用原 `td_batch_pickup_v32`，原批次、流水、收款凭证和欠款沿用同一事务。
- 原始财务凭证、客户共享关系和独立订单不变；无新增财务账本、删除、撤销或冲正入口。
- 操作历史按日期、员工、运单查询。员工只能读本人日志，管理员可读全部；日期按设备当地日界转换。每次最多200条，应缩小日期范围。客户电话仅现有 `customer_edit` 权限（含管理员）显示，不增加员工读电话权限。

## 数据库一致性与审查重点

新增 `td_scan_events_v57` 审计表和私有 `scan_requests_v57` 幂等结果表，均启用 RLS。请求UUID有主键唯一约束，绑定员工、操作和完整请求内容，不同内容不得复用同一请求。普通客户端不能写、改或删审计/请求表。

扫码查询/操作 RPC 使用固定 search_path 与最小显式 EXECUTE 授权，数据库锁定并验证 active/deleted 状态和 V50 权限；匿名拒绝。内部 definer 仅用于受控事务适配及审计，既有 V55/V56 私有schema USAGE 和函数授权保留。

运单表达式索引加事务级 advisory lock + BEFORE INSERT/UPDATE 触发器，防止扫码和原入库同时登记同一规范化运单。历史重复不回填、不清理，现存无运单的包裹保留原行为。**有意的行为变化：原业务录入相同非空运单也会被拒绝，而不是制造重复。** 这是兼容历史重复所采用的等效唯一性保护；并发已在独立数据库连接验证。

批量入库使用逐条子事务，保存每条结果，并在外层同一事务持久化结果与日志；若外层审计/请求写入失败整批回滚。取件不吞异常，任何库存、账目或审计失败整笔回滚。标记表 SHARE 锁与真实业务行锁串行化删除/归档和结算；大批删除并发时可能等待或出现数据库死锁回滚，界面必须核实结果后重试，不会呈现部分完成。

超时不当作“肯定失败”：暂停写入并保留请求UUID，按同一UUID查询结果；请求状态查询也取得相同事务锁，避免将仍在执行的事务误判未提交；未抵达数据库的请求会被封存，迟到请求不得在核实后再执行。刷新只在当前账号 sessionStorage 保存UUID，不保存姓名、电话、图片、密钥或清单；恢复后逐条结果可审计。未提交清单只存在内存，离开/刷新有确认提示；确认放弃或系统终止后需重新扫码。

## 经审批后的安装流程（本次未执行）

1. 管理员审查完整V57迁移；核对预备库与正式库版本，先备份包裹、客户、取件批次/明细、流水、原收款凭证和全部删除标记。
2. 在独立Supabase测试项目安装该单份增量SQL，使用真实项目 RLS/Auth 再验收；本地PostgreSQL不替代托管环境验收。
3. 低峰期在正式Supabase SQL Editor执行完整文件一次。创建索引/触发器会取得表锁，勿在繁忙结算时执行。不重复执行V32至V56。
4. 检查 `td_scan_capabilities_v57`、各RPC EXECUTE、两表RLS及原业务数量、原RPC权限不变。正常启用时无需再部署前端。
5. 仅由管理员选用专门测试运单做首笔试运行；本次不会创建、清理或删除正式业务记录。
